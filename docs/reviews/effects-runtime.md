## 1. Stream every model request and assemble the response

**Current behaviour.** Non-streaming: `OpenAIChatModel.request` is what `FallbackModel.request` (`pydantic_ai/models/fallback.py:229-318`) calls; the runner never sets an `event_stream_handler`, so `request_stream` is never used. Request errors are mapped at `pydantic_ai/models/openai.py:221-236` (`APIStatusError → ModelHTTPError`, `APIConnectionError → ModelAPIError`), which is why the chain falls back today on the ~300s `ReadError`. Per-model `timeout` comes from `model_settings_for` (`llm.py:235-248`) and the client default 180s (:125).

**How to do it inside pydantic-ai (two options, one recommended).**

- Option A: set `event_stream_handler` on every Agent so the graph uses `request_stream`. `DBOSModel` then buffers the stream inside its `model.request_stream` step (:56-80). Cost: every Agent construction site changes (`loader.build_agent`, `runner._ledger/_guard/_browse_guard_agent`, `web_tools.reader_agent`, `evals.py:248`, `cli.py:73`), and fallback semantics change (below).
- Option B (recommended): a `WrapperModel` subclass in `llm.py` whose `request()` opens `self.wrapped.request_stream(...)`, iterates it to exhaustion, and returns `streamed_response.get()` (`pydantic_ai/models/__init__.py:1162-1170`; usage via `.usage()` :1193, `model_name`, `timestamp`, `provider_response_id` all carried). Insert it in `_build_one` (`llm.py:311`) so the order is `DBOSModel → FallbackModel → StreamingModel → OpenAIChatModel`. Nothing above `_build_one` changes; the judges and the reader get it for free; the DBOS step boundary is unchanged; test 1505 still holds.

**What happens to FallbackModel error handling when streaming — the important finding.** `FallbackModel.request_stream` falls back only on errors raised while **opening** the stream; the docstring says it outright: "Mid-stream failures still propagate" (`fallback.py:320-334`). `OpenAIStreamedResponse._get_event_iterator` (`openai.py:3845-3861`) has no `try/except`, `_validate_response` is a no-op (:3909-3917), and the openai SDK's `AsyncStream` only wraps SSE `error` events, never httpx exceptions (`openai/_streaming.py:79,96,189,206`). So a gateway drop after the first byte surfaces as a raw `httpx.ReadError`, not a `ModelAPIError` (`pydantic_ai/exceptions.py:511`), and the chain does **not** fall back. With Option A that error escapes the DBOS step → step retry → whole chain re-run. With Option B the wrapper must catch `httpx.HTTPError` (and any non-`ModelAPIError` exception) around stream consumption and re-raise as `ModelAPIError(model_name, ...)` so `FallbackModel.request` (default `fallback_on=(ModelAPIError,)`, `fallback.py:108`) moves to the spare. That is the one line that makes the plan's "one attempt per model, fallback on error" true under streaming.

**Timeouts under streaming.** httpx's read timeout resets per byte; a model that trickles reasoning tokens will not trip `timeout_s`, so a slow-but-alive request now runs to the step limit (`model_step_limit_s`, `engine.py:79-82`), not the per-model one. A silent hang still trips `timeout_s`. The wrapper should also enforce a wall-clock cap per attempt (`asyncio.timeout(timeout_s)` around consumption) so one model cannot eat the whole chain budget; otherwise `chain_timeout_s` (`llm.py:210-223`) stops describing reality and the watchdog math (`hang_after_s`) is wrong.

**Usage/cost.** Streaming sends `stream=True, stream_options={'include_usage': True}` (`openai.py:1150-1151`, `_get_stream_options` :1429-1436) and sums usage per chunk (:3855-3861). Usage therefore depends on the LiteLLM gateway emitting the final usage chunk. Not verified for `kimi-k3`; the probe counted chunks, not usage. If usage arrives as zero: `runner.execute` accumulates 0 (`runner.py:694-696`), `UsageLimits(total_tokens_limit=token_budget(...))` (:606-610) never trips, `cost_usd` (:632) is 0, `spend_cap_hit` (`backend/src/hq/safety.py:78-84`) never blocks. Guard: in the wrapper, on a 200 response with `usage.total_tokens == 0`, log and estimate (len(text)/4) and mark the row `usage_source='estimated'` in `hq.model_calls`.

**Also affected by the transport rewrite.** `GatewayCompatTransport` returns streaming bodies untouched (`llm.py:58-59`) and only strips `metadata` from JSON bodies; the streaming path never had the `metadata: {weight_versions: [...]}` problem, so that branch becomes dead once everything streams (keep it for embeddings, which are JSON).

**Tests.** Existing: `test_learning.py:1530-1557` (transport 429 wait) unchanged; `:1505-1528` unchanged. Add: wrapper returns a `ModelResponse` with non-zero usage from a fake `request_stream`; mid-stream `httpx.ReadError` → `ModelAPIError`; per-attempt wall clock fires. Frontend/API: none.

**Risk.** Data loss none. Cost: a zero-usage stream is invisible spend (mitigated above). Recovery: unchanged (step re-executes the chain from scratch after a crash — one extra request, no side effects).

## 2. Process-wide semaphore of 5 for the gateway key

**Where.** A module-level `asyncio.Semaphore(5)` acquired in `GatewayCompatTransport.handle_async_request` before the send and released **when the response body is closed**, not when `handle_async_request` returns — a streamed response returns immediately with an open body (:58-59), so releasing on return would let 5 become unbounded. Wrap `response.stream` in an `AsyncByteStream` whose `aclose()` releases; keep the 429 loop inside the held slot (a 429 means another process/key user has the slots).

**Unverified risk (verify first).** An `asyncio.Semaphore` is bound to the loop that first uses it. I did not confirm which event loop DBOS queue workers run async workflows on versus FastAPI's loop (chat turns, REST, Telegram). If they differ, one semaphore silently becomes two. Test: log `id(asyncio.get_running_loop())` inside the transport from a chat turn and a queued task before relying on it; fall back to a `threading.BoundedSemaphore` acquired via `asyncio.to_thread` if they differ.

**Interaction with lanes.** Under the semaphore, 2 task workers + 1 chat + judges + reader + embeddings contend for 5; a long streamed teacher call holds a slot for minutes. Judges are short (p50 7-8s per `runner.py:73-79`) but the reader runs 3 attempts (:241). Ordering is FIFO by `asyncio.Semaphore`; no priority. Expect chat latency spikes during a course build; consider reserving 1 slot for `chat` (two semaphores: 4 shared + 1 chat) if that shows up.

**Tests.** Add: 6 concurrent fake requests → at most 5 in flight; slot released on stream close, not on headers. Frontend/API none.

## 8. The staged lesson writer

**What runs today for a course phase / article.** One `run_task` (`engine.py:408-547`) → `runner.execute` agent loop with tutor's 26 tools; the brief (`course_lesson_brief`, `learning_pipeline.py:1857-1947`, mechanics at :1936-1946; `lesson_brief` :1306-1413, mechanics :1402-1413) tells the model to call `lesson_draft` (`learning_tools.py:678-689`) → `read_course_source` per section (:1211-1248) → `write_lesson_part` per section (:621-676, which runs `part_notes` :578-618 and returns `fix_this_part_now`) → `write_lesson(slug)` (:691-838: `_assemble` :561-566, full-document refusal :750-762, `page_coverage(source, html, note)` :771-780 which includes `lesson_contract` :1525, `page_script_problems` :781-786, `lesson_kit.wrap_page` :787-791, placeholders :793-799, article contract :803-820, file writes :826-838, `lesson.written` event) → `record_lesson` (:319-447) → `_advance_learning` chains hunter's claims check (`engine.py:1625-1653`, `claims_brief` `learning_pipeline.py:1954-2000`, `extract_claim_failures` :2002-2021) → tutor `claims_revision_brief` (:2023-2043) → back to the written stage. `read_course_source_text` (:1170-1172) is the source; the study note comes from `review_tools._study_note` (used at `learning_tools.py:768`).

**What a "section call" is in pydantic-ai terms.** An `Agent[None, str]` (or `output_type=SectionOut` pydantic model) with **no tools**, `instructions` = charter + teaching essentials + kit reference, `Agent.run(prompt)` where the prompt carries the outline, this section's row, its note spans and the previous closing paragraph. One run = exactly one model request. Two ways to make it durable:
- (a) Build the writer agents pre-launch with the same `DBOSDurability` (in `bootstrap_pre_launch`, `engine.py:216-246`) and call `agent.run` **directly in the workflow body**: each request becomes its own `model.request` step with the existing retry/timeout config, checkpointed, fallback chain intact, `model_calls` rows from §3. On a restart the completed sections replay from DBOS step outputs (HTML of a few KB each; fine).
- (b) The `_ledger` pattern (`runner.py:139-152,170-198`): unwrapped agent inside a hand-written `@DBOS.step` with `asyncio.wait_for`. Simpler, but a hung section costs the whole step and gets no per-request checkpoint.
Recommend (a). Per-section budget: `UsageLimits(request_limit=1, tool_calls_limit=0, output_tokens_limit=…, cost_limit=…)` (usage.py has `cost_limit`, per the coordinator's read of :442-520) passed to each `run`; `request_limit` is checked before the request, so a runaway is impossible by construction. Refusal per part: `part_notes(html, earlier_html=…)` becomes the check (today it is advice; promote a subset — predict question missing, no visual, length — to a refusal), re-run that section with the notes appended, at most 2 retries, then continue with the best attempt and flag it.

**What is reused unchanged.** `_draft_dir/_draft_parts/_assemble` (the workflow writes `NN.html` into the same folder so `lesson_draft` still works for ad-hoc runs), `part_notes`, `lesson_contract`, `page_coverage`, `page_script_problems`, `placeholders_in`, `lesson_kit.wrap_page/is_full_document`, `read_course_source_text/split_sections`, `new_claims` (:1420, gives claim candidates for the citation pass), `_study_note`, the `record_lesson` SQL, `claims_brief` for the hunter check (or replace with the citation pass). **What must be refactored:** `write_lesson` and `record_lesson` are `@hq_tool`s taking `RunContext` and raising `ModelRetry` — extract plain functions (`finish_lesson(...)`, `record_lesson_row(...)`) that the tools wrap, so the workflow calls them without a `RunContext`. Their refusal messages name a part only for the shortfall path (:821-824); the concept-count and repeated-sentence refusals are page-wide → map to "re-run outline" (bounded once) rather than every part.

**How it fits DBOS/timeouts.** A new stage handled in `run_task` (branch on `learning.is_course_written(payload)`/lesson stage before `runner.execute`) or a separate `@DBOS.workflow` dispatched by `_advance_learning` — the former keeps `_start_run/_finish_run/_deliver_task_result_step` and the artifact assertion.
