# How the best current systems architect long-running agents, and what Mission HQ should take

All URLs were fetched on 2026-09-23 (by me or by the four research agents whose reports I merged). Pages that could not be opened are listed at the end. Nothing in the repo was changed.

## (a) What "grok bot" and "squad.so" are

### Grok Bot (xAI / SpaceXAI, launched 2026-08-11)

Three things carry the name; the one he almost certainly meant is the product.

1. **Grok Bot, the product.** "AI teammates you can give real work to": persistent, named agents with "their own computer" in the cloud that "keep working 24/7" and "only come back when something needs your approval" (https://x.ai/news/introducing-grok-bot). The design essay (2026-09-03) gives the object model: **Bots** ("persistent agents with their own identity, memory, runtime, and tools"), **Chats** (disposable), **Prompts** usable once, saved as **Skills**, or triggered as **Routines**, **Tools**, **Artifacts**; "Memory and Routines belong to the Bot because they reflect what that particular role knows and does over time" (https://x.ai/news/designing-grok-bot). Official docs facts: all Bots on an account share one cloud computer, "each Bot gets its own screen ... one Bot runs one computer-use task on its screen at a time", up to 50 Bots + group chats, and "For consequential decisions, ask the Bot to check the current source instead of relying on memory" (https://docs.x.ai/grok-bot/overview). A skill lists "when to use it, required inputs and access, the sequence of work, how to validate the result, what to return, what requires approval"; a routine confirmation covers owner, schedule + timezone, input source, expected result, approval boundary and failure handling; "A Bot can own up to 50 routines, and the app keeps the 20 most recent run records"; automation rules: "Automate preparation before execution", "Include a no-data and stale-data policy", "Make retries idempotent where possible", "Tell the Bot where to report partial completion"; after a long absence it asks whether to keep routines running and pauses them if no reply (https://docs.x.ai/grok-bot/skills-routines-and-automations). Approvals: "An approval controls the proposed action. It does not reverse work already completed"; Auto-review has Ask-first and Allow-automatically rules and "If both kinds of rule match, Ask first wins" (https://docs.x.ai/grok-bot/approvals-security-and-privacy). Bot memory = "stable working preferences, important facts, and summaries from its work"; instructions are split into a description (permanent rules, e.g. "Never send external messages without approval") and the conversation (task-specific) (https://docs.x.ai/grok-bot/bots). Group chats of 2–6 bots with a "chief of staff" are marketed (https://composio.dev/content/guide-to-frok-bot, 2026-08-20), but the docs also warn "The screens are separate work surfaces, not separate security boundaries" and "One catch-all helper is weaker than several focused Bots" (https://thearchitecturedeepdive.blog/articles/grok-bot-architecture.html, which cites only official pages). Nothing official describes the model loop, retries, or per-call cost; the reconstructed 0.18 client shows a coordinator routing inference across "Cursor, Claude Code, Codex, OpenRouter backends" with streaming and MCP tool execution, but "does not detail scheduling routines, memory file architecture ... retry logic" (https://github.com/b-nnett/grok-bot-0.18-reconstructed).
2. **@grok on X** is the chatbot, not an agent (https://www.layer3labs.io/guides/what-is-grok-bot, 2026-09-09).
3. **GitHub projects**: `rakazo` (open-source alternative: persistent bots, routines, Postgres + Graphile Worker, Docker/E2B sandboxes, delegation to "peer bots or short-lived subagents", https://github.com/elie222/rakazo) and `grok-ship` ("Scout is investigation ... the deliverable is a report, never a PR"; "Chat is not the source of truth. Projects and tasks live in a sqlite database"; "no pull request until [an adversarial review] pass is clean", https://github.com/kunchenguid/grok-ship).

**Worth taking from Grok Bot**: the skill template with an explicit "what requires approval" and "how to validate the result" section; the routine checklist (no-data/stale-data policy, idempotent retries, where to report partial completion); keeping the last N run records per routine; pausing routines after owner inactivity; "ask-first wins"; "approval does not reverse completed work"; and the "check the source, not memory" rule for consequential facts. Not worth taking: bot-to-bot group chats (unsupported by its own docs, and contradicted by the evidence in (e)).

### squad.so (Squad, "AI Teammates To Do Your Work")

The literal domain is an AI-teammate orchestration product for small businesses: "AI teammates that connect to all your tools, understand your context, and get your work done on schedule"; BYOA ("Bring your own ChatGPT or Claude plan"); $99/month plus your own AI subscription; "Unlimited AI teammates" (https://squad.so, https://squad.so/pricing). Architecture facts on the site: each teammate gets "its own cloud computer, its own access, its own inbox, its own browser"; fallback chains across accounts ("Spend one account and the job continues on the next, mid-task. Spend them all and it falls back to another lab"); "Anything that leaves the building waits for your yes" with per-teammate daily send caps ("18 / 40"); "Every call an AI teammate makes through one of your connections is written down: which account, which file, which rows, at what time"; a "shared context graph and memory"; missions in states Queued / Blocked / In flight / Done (https://squad.so). The demo workspace opens with "4 missions done overnight. Nothing sent without you" (https://squad.so/demo). **Could not find**: docs, blog, changelog, or GitHub for squad.so; the site links none, and the search hits for "Squad" docs belong to other products (`docs.meetsquad.ai` is a different company; `squads.so` is a Solana multisig wallet). So there is no verifiable architecture beyond the marketing page.

Two namesakes worth a glance: **bradygaster/squad** ("AI agent teams for any project" for GitHub Copilot). Agents live in the repo as `.squad/agents/{name}/charter.md` + `history.md`, with shared `decisions.md` ("shared brain"), `routing.md`, `ceremonies.md`; "Each team member runs in its own context, reads only its own knowledge, and writes back what it learned" (https://github.com/bradygaster/squad). Its GitHub Agentic Workflows guide has the most transferable governance mechanics I saw anywhere: retrospectives "wake every six hours", dedupe failures by "failure fingerprint (workflow name, job name, and error line)", improvement proposals are eligible only as "non-executable Markdown under `.squad/skills/**` or `.squad/decisions/inbox/**`" and need a human comment with an `Approved-Revision` hash; workers "remain draft-only; neither reviews its own output, marks ready nor merges"; hard caps per run (50 issues, 5 action issues per report) and "if a cap was actually reached, the report names which cap" (https://bradygaster.github.io/squad/docs/guide/gh-aw/).

**Worth taking from squad.so**: the per-teammate daily cap on outward actions, the per-connection audit row, the one-line morning summary ("N done overnight, nothing sent without you"), and account-level fallback for capacity. From bradygaster/squad: a `decisions/inbox` quarantine that agents write to and only the owner promotes; prompt/skill changes proposed as markdown and approved by hash; failure fingerprinting to dedupe incidents.

## (c) Ten architecture decisions Mission HQ should adopt

Each names the module and the source where it is shown working.

**1. `llm.py`: bound every call by idle time, classify the error, and only then fall back.** Stream, and fail the attempt when no chunk arrives for N seconds (OpenClaw: model idle timeout 120s cloud / 300s self-hosted, "A terminal timeout is a failed turn", https://docs.openclaw.ai/concepts/agent-loop) plus a total cap. Classify: 429 → wait for a slot with cooldown (OpenClaw retries rate limits "up to 10 total attempts" with 30s→1m→5m cooldowns before rotating, https://docs.openclaw.ai/concepts/model-failover); timeout/5xx → next model in the chain; context overflow → never fall back, shrink the input (same page; pydantic's `FallbackModel` triggers on any `ModelAPIError` 4xx/5xx, https://pydantic.dev/docs/ai/models/overview/, so a raw FallbackModel would send an overflow to a smaller-context model). Record one row per attempt with `cache_read`/`cache_write` tokens (Anthropic cost tracking, https://code.claude.com/docs/en/agent-sdk/cost-tracking) and the price version used, because LangSmith notes price changes are not applied "to traces already logged" (https://docs.langchain.com/langsmith/cost-tracking).

**2. `engine.py`: replace the process semaphore and lanes with a DBOS queue.** `global_concurrency=5` (the gateway key), `limiter` for burst, `priority` so chat outranks nightly tasks, and `deduplication_id = f"{cron}:{slot}"` so a restart cannot enqueue a slot twice (https://docs.dbos.dev/python/tutorials/queue-tutorial). A queue survives the ~110 restarts; a semaphore does not. LangGraph's server does the same with `N_JOBS_PER_WORKER` and double-texting policies (https://docs.langchain.com/langsmith/env-var, https://docs.langchain.com/langsmith/double-texting).

**3. `runner.py`: crons do not backfill; they skip overlaps, stagger, and auto-pause.** DBOS `automatic_backfill=False` and "executed by exactly one worker" (https://docs.dbos.dev/python/tutorials/scheduled-workflows); Claude Managed Agents: "Missed triggers are not backfilled", jitter up to 15% of the interval, rate-limited runs "recorded ... without retry", deployments auto-pause on unrecoverable errors (https://platform.claude.com/docs/en/managed-agents/scheduled-deployments); Temporal overlap policy `Skip` (https://docs.temporal.io/schedule); OpenClaw staggers top-of-hour jobs by up to 5 minutes and alerts "after 2 consecutive failures with a 1-hour cooldown" (https://docs.openclaw.ai/automation/cron-jobs/schedules, https://docs.openclaw.ai/automation/cron-jobs/delivery). Concretely: a `hq.crons` row with `consecutive_failures`, `paused_reason`, `last_slot`; pause after 2 failures; one notification, not one per failure; and the Grok Bot rule of asking whether to keep routines running after the owner has been away (https://docs.x.ai/grok-bot/skills-routines-and-automations).

**4. `loader.py`: token budgets enforced at load, static-first ordering, and a prompt-bundle hash per run.** Claude: skill metadata ~100 tokens always on, body under 5k tokens and 500 lines, CLAUDE.md under 200 lines (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview, https://code.claude.com/docs/en/memory); OpenClaw: 20,000 chars per bootstrap file, 60,000 total, with a truncation notice injected (https://docs.openclaw.ai/concepts/context); Hermes: MEMORY.md 2,200 chars (https://hermes-agent.nousresearch.com/docs/user-guide/features/memory). Order the bundle charter → card → skills → memory blocks → brief so the stable prefix caches (OpenAI: "Put stable developer instructions and shared reference material first", https://developers.openai.com/api/docs/guides/prompt-caching; Manus: "Keep your prompt prefix stable", https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus). Store the SHA of the assembled bundle in `hq.runs` so evals and incidents pin a version (Managed Agents sessions pin an agent `version`, https://platform.claude.com/docs/en/managed-agents/sessions; OpenAI's replacement for prompt objects is git + "lightweight eval fixtures", https://developers.openai.com/api/docs/guides/prompting/migrate-from-prompt-object).

**5. `learning_pipeline.py`: the staged writer as a DBOS workflow with idempotent section steps and a compact carry-forward.** The plan's outline → sections → assemble matches prompt chaining "with gates" (https://www.anthropic.com/engineering/building-effective-agents), the three-agent harness where "one agent would write a file, another agent would read it" (https://www.anthropic.com/engineering/harness-design-long-running-apps), Devin's dynamic workflows for "staged pipelines" where "completed agents replay their recorded results instantly, and only the unfinished work runs again" (https://docs.devin.ai/work-with-devin/dynamic-workflows.md), and Manus Wide Research giving each sub-task "its own dedicated context" (https://manus.im/docs/features/wide-research.md). Implement each section as a step keyed by `lesson:section:outline_sha`, fanned out on the queue at concurrency 3, with the citation pass as a child workflow. Add the Cognition caveat: because "Actions carry implicit decisions" (https://cognition.com/blog/dont-build-multi-agents), pass every section the outline plus a code-maintained list of terms and claims already introduced (the instruction-review's "assumed terms ⊆ introduced ∪ known" check), not only the previous closing paragraph.

**6. `engine.py`: stall counter in code, then replan with a cleared context, then stop with a report.** Magentic-One increments a stall counter when the ledger sees no progress or a loop; above the threshold ("≤2 in our experiments") it re-plans and forces "all agents to clear their contexts and reset their states"; termination is by max attempts or time, reporting "a final answer, or its best educated guess" (https://arxiv.org/html/2411.04468). Agent Framework defaults: `max_stall_count=3`, `max_reset_count=2` (https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic); 12-factor: "~3 attempts" then "escalate to a human" (https://github.com/humanlayer/12-factor-agents). Stall signals stay deterministic (same tool + same args, no artifact delta); the model is asked only for the new plan.

**7. `memory.py`: consolidation emits operations, code applies them under caps, into a candidate the owner promotes.** OpenClaw dreaming: "The model returns operation decisions, not replacement memory prose", deep phase is the only durable write, `maxPriorEntryLossFraction: 0.25`, untrusted provenance removed (https://docs.openclaw.ai/concepts/dreaming); Managed Agents dreams produce a new store, "input store is never modified", for review, with immutable versions (https://platform.claude.com/docs/en/managed-agents/dreams, https://platform.claude.com/docs/en/managed-agents/memory); Deep Agents: "human-in-the-loop validation before the agent writes to shared memory" (https://docs.langchain.com/oss/python/deepagents/long-term-memory); Devin Knowledge is human-curated with a required trigger description and auto-suggested from feedback (https://docs.devin.ai/product-guides/knowledge.md). Memory blocks are `read_only` for every agent except the consolidation run (Letta: shared blocks need one owner or "lost updates", https://docs.letta.com/guides/agents/multi-agent-shared-memory). The bradygaster/squad `decisions/inbox` pattern is the same idea for the quarantine (https://bradygaster.github.io/squad/docs/guide/gh-aw/).

**8. `tools/` + `engine.py`: a declared effect per tool drives approval; approval never reverses; runs park while waiting.** Each tool declares `effect: read | reversible_write | outward` (OpenAI's guide rates tools by "read-only vs. write access, reversibility, required account permissions, and financial impact", https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf); resolution order deny → ask → allow with "Ask first wins" (https://docs.x.ai/grok-bot/approvals-security-and-privacy; Claude: hooks → deny → ask → mode → allow, https://code.claude.com/docs/en/agent-sdk/permissions). A waiting run must not hold a queue slot: use `DBOS.recv` with a timeout so the workflow parks durably (https://docs.dbos.dev/python/tutorials/workflow-communication; Agent Framework Durable: pause "without consuming compute or model tokens", https://learn.microsoft.com/en-us/agent-framework/hosting/azure-functions). Add per-agent daily caps on outward actions (squad.so "18 / 40", https://squad.so) and a per-run budget copied from the task kind, checked between model calls (Managed Agents, https://platform.claude.com/docs/en/managed-agents/budgets).

**9. `backend/evals/` before the prompt rewrite, with graders in a fresh context and failures fingerprinted.** Anthropic: "20-50 simple tasks drawn from real failures", regression sets held at ~100% (https://anthropic.com/engineering/demystifying-evals-for-ai-agents); "Create evaluations BEFORE writing extensive documentation" (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); Managed Agents grader "uses a separate context window", `max_iterations` default 3 (https://platform.claude.com/docs/en/managed-agents/define-outcomes); LangSmith turns negative-feedback traces into dataset examples (https://docs.langchain.com/langsmith/evaluation-concepts); Letta evals fail CI with a non-zero exit (https://www.letta.com/blog/letta-evals/). The outline and citation judges therefore see only the rubric and the artifact, never the writer's transcript; revision loops stop at 3; each incident gets a fingerprint (bradygaster/squad: "workflow name, job name, and error line") so the same failure is one case, not eight dated rules.

**10. `runner.py` + `engine.py`: fresh session per scheduled run, explicit continuity, and restorable tool results.** Claude routines: "Each run creates a new session" (https://code.claude.com/docs/en/routines); Codex automations "start a new chat for each scheduled run" (https://learn.chatgpt.com/docs/automations?surface=app); Hermes cron injects the previous run's output with `continuity=True` (https://hermes-agent.nousresearch.com/docs/user-guide/features/cron); OpenClaw's isolated heartbeat cut "~100K tokens down to ~2-5K per run" (https://docs.openclaw.ai/gateway/heartbeat). Drop the stale `memory/agents/<agent>.md` injection; put the last run's record in the brief. In the loop, store any tool result over ~4,000 chars as an artifact and replace it in history with a pointer after the next turn (OpenClaw soft-trim to first/last 1,500 chars, https://docs.openclaw.ai/concepts/session-pruning; Manus: drop page content, keep the URL, "restorable", https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus). This is what stops the 80,000-token calls in the instruction review.

**Frontend**: an approvals queue with per-agent daily caps and a run timeline, a one-line morning summary ("4 missions done overnight. Nothing sent without you", https://squad.so/demo), a promote/drop view for the consolidation candidate, and the cron table with pause reasons. All are data the decisions above already produce.

## (d) Where the existing plan disagrees with the evidence

1. **"One attempt per model; FallbackModel on ModelAPIError" (plan §6).** The systems with real uptime distinguish error classes: rate limits are waited out with cooldowns, context overflow never triggers fallback, only timeouts and server errors do (OpenClaw failover; pydantic's FallbackModel fires on every 4xx/5xx). One attempt per model is right for timeouts; wrong for 429 and overflow. Change §6 to the classification in decision 1.

2. **Build order puts evals last (Phase 8).** Anthropic and OpenAI both put eval fixtures before or alongside prompt changes; the plan's Phase 2 rewrites 35,900 words of prompts with no regression set in place. Move a 20-case regression set (from the incidents the plan already lists) ahead of Phase 2; grow it in Phase 8.

3. **"Cron catch-up creates only the newest missed slot" (§6).** Every platform fetched that runs schedules (Claude scheduled tasks and Managed Agents, OpenClaw, DBOS default) does not backfill at all; overdue work is rescheduled to the next slot. Newest-slot is defensible for the nightly export, but simpler and safer is `automatic_backfill=False` plus overlap `Skip` and a dedup key. Also add auto-pause after consecutive failures, which the plan lacks.

4. **"Lanes: tasks at 2, chat at 1, under the semaphore" (§6).** An in-process semaphore resets on every restart and cannot prioritise. The durable queue with priority (decision 2) replaces both lanes and the semaphore.

5. **"Approval waits have a timeout and a fallback (skip and continue, or end the run)" (§6).** Managed Agents, the Agents API, and Durable Agent Framework let sessions wait indefinitely because a parked run costs nothing. The timeout exists in the plan only because a waiting run holds a lane. With `DBOS.recv` the run parks; keep a long timeout for hygiene, but the lane problem disappears.

6. **Sage absorbs librarian as a `consolidate` skill inside one loop (§4, decision 2).** Skills run inside the calling session and "accumulate context tokens across the conversation" (https://docs.langchain.com/oss/python/langchain/multi-agent); Letta and OpenClaw both run consolidation as a background job in an isolated session. Merge the identity and the instructions, but run consolidation as its own scheduled, isolated, read-mostly workflow, never inside the chat loop.

7. **Consolidation: "code with a model judgement step ... the diff is reviewable the next morning" (§7).** The evidence is stricter: the model emits operations, code applies them under a loss cap, the result is a candidate that does not replace the live memory until promoted (decision 7). "Apply, then review the diff" is the weaker form.

8. **Stall handling: "the LLM judge runs only on stall" (§6).** Magentic-One's response to a stall is a replan with cleared context and a bounded number of resets, then a best-effort report. The plan's judge should return a new plan, not a verdict, and the run should end with a report after two resets.

9. **Word targets per run (§5) with no measurement.** Claude Code, OpenClaw and Hermes enforce in tokens/chars at load time with truncation or refusal. The word counts are fine as targets; `loader.py` must enforce a token budget and `prompt-check` must fail over budget (decision 4).

10. **Model policy silent on caching.** OpenAI charges cache reads at 0.1×; Manus reports 0.30 vs 3 USD/MTok cached vs uncached. Whether the gateway's kimi models cache is not on any fetched page (could not verify), so the plan should at least order the bundle static-first and record cache tokens so the question can be answered from `hq.model_calls`.

Where the plan already agrees with the evidence and should not move: fixed artifacts between stages (§3.4), enforcement in code (§3.1), incidents become tests (§3.3), read-mostly isolated roles (§3.6; Cognition and Anthropic's research system both keep sub-agents to read-only work), single owner-facing notifier (Grok Bot "only pull you in for judgment calls"; Hermes "alert once"), per-part refusals, and the citation pass with a separate cheap judge.

## (e) Fashionable, not supported by the evidence: skip

- **Agents that message each other / group chats.** Grok Bot markets 2–6 bot group chats, but its own docs warn against treating bots as boundaries; Cognition's "Don't build multi-agents" and Anthropic's research system (sub-agents read-only, "15× more tokens than chat" per LangChain's blog) point the other way; Microsoft says Magentic orchestration is "untested ... outside the original Magentic-One design". Mission HQ's roles are for isolation and tool scope, not conversation. Keep it that way.
- **A per-turn LLM progress ledger.** Magentic-One's ledger works on 20-turn benchmark tasks; Mission HQ's own data (91.5% "satisfied", one 3.6-hour hang) shows the cost. Counters in code, model only on stall.
- **An LLM planner injected into every task** (CrewAI runs `gpt-4o-mini` planning before each iteration). Plan only where the plan is an artifact that gates the next stage (the lesson outline).
- **Continuous heartbeat / sleep-time agents.** OpenClaw's heartbeat defaults to every 30 minutes; Letta's dreaming "uses more model tokens and does not ask you for approval". Mission HQ has nothing ambient to watch; one nightly consolidation with review is enough.
- **Vector memory as the primary store.** Letta's new MemFS ships with "no semantic index by default"; OpenClaw and Hermes load a small markdown snapshot and search only on demand. The vault plus grep/FTS is the mainstream now; embeddings are an optional add-on.
- **Opaque server-side compaction** (OpenAI's encrypted compaction item "not intended to be human-interpretable"). A personal system that wants reviewable memory should hand off through files and per-stage artifacts instead.
- **Hosted prompt and eval platforms.** OpenAI is shutting down prompt objects, the Evals platform and Agent Builder on 2026-11-30 and tells users to move prompts to git with eval fixtures. Keep prompts, skills and evals in the repo.
- **Big always-on memory.** Managed Agents allow 100 kB per memory; the personal systems (Hermes 2,200 chars, OpenClaw 20k chars per file) stay small. The plan's 4k-char blocks are on the right side.
- **Teach-by-demonstration skills and computer-use for everything** (Grok Bot). Prefer a connector when one exists is Grok's own rule; Mission HQ's operator stays the last resort under its contract.
- **Switching frameworks.** LangGraph and Temporal offer nothing DBOS lacks for this workload; note only that pydantic-ai says `DBOSAgent` "will be removed in v3" in favour of durability capabilities, so pin the version and plan the migration.
