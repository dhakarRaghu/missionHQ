What did you actually read this week?

Split the server in two: the median does not move

Prefill and decode shared one GPU, and their interference landed on the tail, not the middle. Splitting them onto two GPUs left the median untouched. It cut the p99 about sixfold, because rare long jobs leave most requests alone. The split also charged every request a KV transfer, which tripled TTFT on the box with no peer-to-peer link.

The Client Under Stress (Phase 5A)

A bare timeout=600 is four independent idle deadlines. The read timeout resets on every chunk, so none of them bounds the total stream. A dead stream can hang ten minutes while looking configured. Under overload, only a policy that sends less recovers. Backoff with jitter tied blind retry at 22.7% in the measured table.

Up, Fast and Wrong (Phase 5B)

A feature can be up, fast and wrong. So quality needs its own SLI: a ratio of threshold-crossing events, never a mean score. That ratio becomes an alert only through burn rate. Bad rate over allowed rate is measured across a long window for severity and a short window to confirm.

The 2% Hack Rate and the 67% Leak

A reported hack rate names its checker, so it bounds what you detected, never what the environment leaks. The 2% confirmed-hack number sat beside 67% of environments that still leaked. It leaked through orphaned git fsck objects and caches nobody listed. Block one route and the agent takes the next, so you enumerate channels, not tools.

Why adding replicas did not fix the slowest replica

Uniform session hashing over S replicas is a Poisson process whose variance equals its mean. So the relative load spread never shrinks as you add replicas. Scaling from 4 to 8 replicas halves every load but leaves the same share of replicas far above the mean. The fix is placement by measured load, not more replicas.

Which five things are still worth having in six months?

You have just re-read the five lessons as cards. Here are the five claims, stated as sentences you can now check yourself against. Each one earns its place because it names an observer or a mechanism that a trusted number hides. Each will still be true after the tools in it are replaced.

  1. Interference lands on the tail, not the median. When two workloads share one processor, rare long jobs pause only the requests unlucky enough to overlap them, so the median stays flat while the p99 climbs. Splitting prefill and decode onto two GPUs left the median alone and cut p99 ITL about sixfold. From "Split the server in two: the median does not move." It lasts because it is a property of any shared queue, not of one GPU model.
  2. A read timeout is a stall detector, never a deadline. It resets on every chunk that arrives, so a stream that drips one token per minute is "healthy" while a dead stream waits the full timeout. A bare timeout=600 is four independent ten-minute idle waits, and none of them bounds the total call. From Phase 5A, "The Client Under Stress". It lasts because every HTTP client resets the read timer this way.
  3. Under overload, only a policy that sends less recovers. Backoff delays retries without reducing them: in the measured table, backoff with jitter tied blind retry at 22.7%. The fix order is one retry layer, a retry budget, full jitter, then a breaker that sheds load. From Phase 5A, "The Client Under Stress". It lasts because the arithmetic behind it is a queue, and queues do not change with SDK versions.
  4. Quality gets a budget only as a ratio, and an alert only through burn rate. A mean score hides degradation, so the SLI counts events that cross a threshold. Burn rate is bad rate over allowed rate, measured on a long window for severity and a short window to confirm it continues. From Phase 5B, "Up, Fast and Wrong". It lasts because it is the only form that connects a judgement to a pager without paging constantly.
  5. Uniform session hashing is Poisson, so the relative spread never shrinks. Poisson variance equals the mean, so scaling from 4 to 8 replicas halves every load but leaves the same share of replicas far above the mean. The fix is placement by measured load. From "Why adding replicas did not fix the slowest replica". It lasts because it is arithmetic about hashing, not about any router.

Can you still answer three questions from three weeks ago?

The keepers above were all lessons from this week. The three questions below go back three weeks, to Phase 0, Phase 1 and Phase 2A, where the numbers are older and easier to lose. Write each answer before opening the sketch. Matching the mechanism matters more than matching the digits.

  1. Prefill against decode. You send one prompt of 10,000 input tokens to a model served on one A100 GPU. About how many output tokens would buy you the same wall-clock time?
    Answer sketch

    Prefill is compute-bound and decode is bandwidth-bound, so the crossover is the GPU's compute rate divided by its bandwidth.

    312e12 FLOP/s ÷ 1.5e12 B/s ≈ 208 tokens
10,000 input tokens ÷ 208      ≈ 48 output tokens

    About 48 output tokens, because each decode step loads the full model weights while 208 prompt tokens process in parallel. Real bandwidth is about 90% of the rated number, which pushes the practical answer to about 43. The same arithmetic on an H100 gives a crossover near 295, from published specs, not a measurement. (Phases 0 and 1)

  2. The capacity setting that looks like a safety setting. On one 80 GB GPU serving llama-3-8b, you lower vLLM's gpu_memory_utilization from the 0.92 default to 0.70. What does it cost?
    Answer sketch

    The fraction does not guard memory. It decides how large the KV cache pool is, and pool size decides concurrency.

    (0.92 − 0.70) × 80 GB = 17.6 GB  lost from the KV pool
concurrency: 260 → 181 requests  (llama-3-8b, 80 GB)

    The KV pool, the memory the GPU reserves for attention state, shrinks by 17.6 GB and concurrency falls by about 30%, while the mean latency barely changes. That is the trap from Phase 2A: it reads as a safety margin and behaves as a capacity setting. vLLM 0.29.0 defaults to 0.92.

  3. Is the prefix cache broken? You raised the prefix cache block size from 16 to 64 tokens, and the hit rate on your stable-first prompt layout fell. Is the cache broken?
    Answer sketch

    No. A prefix cache matches whole blocks from token 0 forward, so a larger block shares less at the edge of a prefix: one changed token inside a 64-token block invalidates all 64. The Phase 2A lab showed exactly this. At block size 16 the stable-first hit rate was 92.0%; at 64 it fell to 91.5%, and the saving moved from 3.22x to 3.19x. The cache is working as designed. If the rate had fallen far more than that, then you would suspect prefix identity instead, for example an injected timestamp at the prompt head. (Phase 2A, and the routing lesson's cache reasoning)
