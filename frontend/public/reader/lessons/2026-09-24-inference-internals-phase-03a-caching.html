The Bill and the Cache

Your Phase 1 meter over-bills every cached request and cannot prove a cache hit. What does a correct meter have to see?

Phase 0 had a timestamp bug that cost four months of full-price agent steps. The fix was one line. The expensive part was that nobody had a number that could show the loss. When you built a meter in Phase 1, it priced every input token at the full rate. That meter cannot show a cache saving, because it cannot see the field the saving lives in.

Here is the sharper failure. A dashboard can show 20 input tokens for a 40-turn agent run with a 20,000-token system prompt, and nobody questions it. The number is small and plausible. The hole in it is invisible from the inside, because the missing tokens were priced at the cache rate, not the full rate, so the total cost also looks plausible. This lesson is about reading a real usage object correctly. Which tokens count as input is a provider contract, not a standard. A cache hit is a byte-exact match that fails silently. And caching is a purchase with a break-even point, not a free optimization. The question the lesson leaves open: given a real usage object from either provider, can you say what the run actually cost and prove the cache worked?

Why your Phase 1 meter is wrong about every cached request

Phase 3A turns the prefix cache you already understand into numbers on an invoice.

You already own the mechanism. Phase 2B taught you the prefix rule: a cache hit needs identical tokens from position zero. It taught you the radix tree: the server stores prefixes and shares them across requests. Phase 1 gave you the two-price formula: input tokens times the input rate plus output tokens times the output rate.

This phase is the billing side of the same mechanism. The prefix rule now has prices attached. A reused prefix reads at a fraction of the input rate. A fresh prefix can cost a write premium above it. So your Phase 1 formula mis-bills every cached request, in both directions. It overstates cached runs and misses write premiums.

Four claims carry the phase, in the order above. The usage object itself is a provider contract, not a standard. Detail counts decompose the total, and a missing price falls wherever your fallback puts it. Caching is a purchase with a payback period, not a free switch. And a cache hit is a byte-exact prefix match whose failure is silent, so only the cached-token count proves it.

Two things from here feed Phase 3B directly. The batch multiplier is one of the request-level multipliers this phase defines. The cost alarm in 3B is the detector for the silent cache regressions this phase describes. The batch-and-caching question stays open until then.

Are cached tokens inside or outside your input count?

The same field name counts cached tokens at different providers, so your summation needs an adapter per provider.

You write a cost meter against one provider's usage object. It passes its tests. Then a second provider feeds it, and every cached run reports the wrong cost. The meter was never broken. The contract changed under it.

Predict: Your dashboard shows 20 input tokens for a 40-turn agent with a 20,000-token system prompt. What should that number have made you suspect, and why did it survive code review?

The prompt alone needs 20,000 tokens per turn, so 20 total input is impossible. The meter had to be missing the cached fields. It survived review because nothing crashed. The number it printed was small and shaped like a real number, and no test asserts that an input count is plausible for the prompt that produced it.

The same field name, two opposite contracts

Today the two major providers put cached tokens on opposite sides of the base count.

On OpenAI, cached and cache-write tokens sit inside input_tokens. So fresh input is what is left: ordinary input = input_tokens − cached − cache_write. Add the cached classes back and you double count.

On Anthropic, they sit outside. input_tokens there counts only the tokens after the last cache breakpoint. Total input is cache_read + cache_creation + input_tokens.

OpenTelemetry, the observability standard this pipeline stacks converges on, normalizes to the OpenAI shape. Its gen_ai.usage.input_tokens should include every input token type, cached ones included. So an adapter that forwards Anthropic's raw input_tokens into an OTel pipeline under-reports, and everything that recomputes cost from tokens downstream inherits the hole.

Which parts of the bill are not token counts at all?

Your meter reads token counts. Part of the bill is not a token count at all, and misreading that part can double a reported cost.

Predict: your multimodal meter reports 500 input tokens as 300 total plus 200 image tokens, billed as 500. What is wrong, and which direction does the error go?

The meter added a subset to its own total. The 200 image tokens are inside the 300. The real bill is 300 input tokens, so the meter over-reports by 200.

The direction is upward. Every modality detail field it adds inflates the bill. In the limit it reports up to double the real cost.

The wrong belief is that nested detail counts sum up to the total. Actually they decompose it. The total is what you are billed on. The details tell you which tokens inside it cost more. The OpenTelemetry registry states this with a worked example:

usage.input_tokens          300   ← the total you are billed on
  text.input_tokens         100   ┐
  image.input_tokens        200   ├ subsets: they SUM to the total
  text.cache_read            40   ┘ cached overlaps text, so it adds neither

WRONG:  300 + 200 = 500 billed      (the 200 counted twice)
RIGHT:  300 billed, of which 200 carry the image price

One request carries 100 text tokens, 40 of them cached, plus 200 image tokens. The billed input count is 300. A meter that adds the nested fields to the total bills 500. It can report up to double the real bill on multimodal traffic.

Which direction does your meter err when it cannot price a class?

An unpriced class never stays neutral. It takes whichever value your fallback sets.

Your meter meets a token class with no price on the sheet. Cache reads on a new model, a tier you have not seen. The code must still emit a number. That number comes from a default you chose earlier, and it chooses the direction of every error you are about to make.

Only two defaults exist. Default to zero, and the class looks free. Default to the full rate, and the class looks expensive. Neither throws an exception. They differ in who notices.

Fallback to zero.

cached_rate = price.cached_input_per_mtok or 0.0

Every unpriced class makes the request look cheaper than it is. The error grows silently as you add models whose sheets you have not filled in. Nothing ever contradicts it, because no invoice shows a saving.

Fallback to the dearest rate.

cached_rate = (price.cached_input_per_mtok
               if price.cached_input_per_mtok is not None
               else price.input_per_mtok)

You over-report until you fill in the sheet. Over-reporting contradicts the invoice, so someone notices, investigates, and finds the missing price.

The zero default is the worse error because nothing detects it. A dashboard that says you are saving money you are not saving looks healthy. A dashboard that says you spend more than the invoice looks broken, and broken things get debugged. inferred Which direction your gaps bend is your decision, not the library's.

Over-reporting has its own cost, and it is not silence. It hides the wrong things.

  1. It hides your wins. Caching already cut your bill in half, but a meter that prices cache reads at the full rate cannot see it. You cannot prove the work mattered, and you cannot see it stop working.
  2. It breaks comparisons. A routing choice between two models is a ratio. One model caches and one does not. An overcharging meter compares them on the wrong basis and can pick the wrong model.

The durable rule sits next to it: every price on the sheet carries the date it was read. Prices change in every release. A price in your repository with no priced_on beside it cannot be audited, so it is not a fact, only a number. When the sheet is filled in weeks later, the date tells you which past reports to distrust.

When does caching cost more than no caching?

Caching is not a free discount. Every write costs more than the uncached rate, and every read costs less. Whether the feature saves you money depends on one number: how many times each entry gets read before it expires.

Predict: Ten identical requests fire in parallel at cold start, all carrying the same 12,000-token prefix, writes at 1.25x. Is that burst cheaper or more expensive than the same ten with caching off?

More expensive, by a factor of 1.25. A cache entry becomes usable only after the first response begins. All ten requests start before any entry exists. You get ten writes at 1.25x and zero reads. Caching off would have cost 10x. The burst costs 12.5x.

The derivation is arithmetic, not judgement. A write costs more than a normal input token. A read costs less. So the trade turns positive after a fixed number of reads.

extra cost to write   = (write_rate - input_rate) x tokens
saving per read       = (input_rate - read_rate)  x tokens

reads needed to profit = (write_rate - input_rate) / (input_rate - read_rate)

Put in the verified multipliers. A 5-minute write costs 1.25x input. A read costs 0.1x. The break-even is (1.25 - 1.00) / (1.00 - 0.10) = 0.28 reads, so one read already profits. A 1-hour write costs 2x. The break-even is 1.11 reads, so two reads profit. The formula survives every price change. The numbers carry their model and date, and both do change.

This is a payback-period picture. Draw cost per turn for a cached run and a control run. The cached run starts above the control because turn 1 pays the write premium. Each read then drags it below. The crossing point is the break-even turn.

Evidence

Multipliers verified at both providers' prompt-caching docs, read 2026-09-23: 1.25x writes and 0.1x reads on OpenAI GPT-5.6 and later, 1.25x 5-minute and 2x 1-hour writes with 0.1x reads on Anthropic's common models. OpenAI's doc states the amortization directly: "Writing a prefix once and fully reusing it once costs 1.35x its ordinary input cost, compared with 2x for processing it twice without caching". One write plus nine reads costs 2.15x against 10x uncached. The cold-start rule, an entry usable only after the first response begins, is from Anthropic's doc.

The cold-start fan-out is the expensive version of this rule, and the phase's table makes it concrete. Ten calls share a 12,000-token prefix, at input $2.00, write $2.50, read $0.20 per million tokens.

All ten at once: 10 writes, 0 reads. Cost 10 x 12,000 x $2.50 / 1e6 = $0.300. No caching at all costs $0.240. You paid 1.25x to save nothing.

One warm-up call, then nine: 1 write plus 9 reads. Cost $0.0300 + $0.0216 = $0.0516. Same work, nearly 6x cheaper than the uncached burst.

The fix is a prewarm. Both providers now ship one as a first-class feature, and the phase omitted both. OpenAI has prompt_cache_options.prewarm: true, which prepares the cache without generating output. Anthropic uses max_tokens: 0, which writes the entry at your breakpoint and returns at once with zero output tokens billed. One warning on the Anthropic version: the prewarm must use the same thinking and effort configuration as the real traffic, or the entry is never hit.

Google bills differently again: cache storage by the hour. An idle entry costs nothing on OpenAI and Anthropic, and money on Google. The dollar figure is a lookup on their pricing page. The mechanism is the part to keep.

Why did your cache silently stop hitting?

Your cache failed silently, and only the cached-token count can tell you it did.

You enabled caching. No error ever appeared. Yet the invoice did not move. This section is why, and how you prove the cache works at all.

Predict: your team enabled prompt caching and the invoice did not move. Give three separate causes, and the one number that distinguishes them.

Three causes. First, a volatile field sits above the breakpoint, like a timestamp. Every request then writes a fresh entry and never reads. Second, something hands the provider reordered bytes, like a Go map serialized with random key order. Third, the prefix sits below the cacheable minimum. That fails with no error.

One number distinguishes them: the cached-token count in the usage object. Zero cached tokens with full write counts says the prefix changes. All zeros says below the minimum, or nothing marked.

The match is byte-exact from token 0, not a match on meaning. The provider hashes the prefix cumulatively, in a fixed order: tools, then system, then messages. A changed byte at any level breaks that level and every level after it. So an edit to one tool definition breaks everything. A new user message breaks nothing above it.

the cache prefix, hashed from token 0 downward

┌─────────────────────────────┐
│ tools                       │  ✗ changed byte, or Go/Swift map
├─────────────────────────────┤    keys reordered: breaks ALL levels
│ system                      │  ✗ changed effort, thinking, or a
│   (wildcard setting)        │    setting: breaks system + messages
├─────────────────────────────┤
│ messages                    │  ✗ below the minimum: silent no-op,
└─────────────────────────────┘    no error returned

proof: usage.cached_tokens — the single truth gauge

The invalidation list is longer than the phase showed. Anthropic warns that thinking and effort configuration change the hash too. On OpenAI, model, tool definitions and their order, parallel_tool_calls, the structured-output format, reasoning effort, verbosity, and context management all invalidate. One language-level trap deserves its own sentence: Go and Swift randomize JSON map key order. Your tool schema then serializes differently per process. Your hit rate depends on which pod ran the serializer. The fix is a fixed key order where you serialize schemas.

Below the minimum, the failure is a silent no-op. The Anthropic doc states it directly: shorter prompts cannot be cached, even when marked with cache_control, and no error is returned. The minimums run from 512 to 4,096 tokens by model. Treat that range as a lookup, not a memory.

One rule corrects a common reading of the lookback. The 20-block backward lookback finds entries that prior requests wrote at their own breakpoints. It does not find stable content that happens to sit behind your breakpoint. A volatile block above the breakpoint therefore means a fresh write every request, and never a read. For your agent loops: a run of consecutive tool_use blocks, and a run of tool_result blocks, count as one position each in that lookback.

One paragraph on multi-tenant systems. OpenAI now frames a separate prompt_cache_key per customer as a defence against cache-hit probing across users. Without it, one tenant can in principle detect which prefixes another tenant used by timing responses. You build multi-tenant agents. Put the customer id in that key.

Measured proof that layout drives the hit rate. ProjectDiscovery runs an agent platform: tasks average 26 steps and 40 tool calls, with system prompts over 20,000 tokens. They moved dynamic content out of the cacheable prefix. The hit rate rose from about 7 percent to about 74 percent in one deployment, later about 84. Cost savings ran 59 to 70 percent. Their sharpest pair: two tasks with nearly the same token volume, one at a 91.8 percent cache rate, one at 3.2 percent. The second cost roughly 60 times more.

Where do you place the breakpoint, and for how long?

Breakpoint placement and TTL set whether you ever reach break-even.

Implicit caching from earlier sections picked the boundary and the lifetime for you. Explicit caching hands you both. Each choice has a price, so each needs its own arithmetic.

A breakpoint writes exactly one entry

A breakpoint is a content block you mark with cache_control. The mark writes one entry. The entry is a hash of everything up to and including that block. Earlier positions get nothing.

system blocks                                  what gets cached

┌──────────────────────────────┐
│ tool definitions             │  ─┐
├──────────────────────────────┤   │  the entry is a hash of
│ policy text, 8,000 tokens    │   ├─ EVERYTHING up to and
│   cache_control: ephemeral   │  ─┘  including this block
├──────────────────────────────┤
│ today's date, session id     │      below the breakpoint:
└──────────────────────────────┘      never cached, and it
                                      cannot break the entry

You get at most 4 breakpoints per request. A fifth returns HTTP 400. Use them for layers with different change rates. One for tools. One for policy text. One for the conversation tail.

The next request hashes the prefix at your breakpoint and looks for a match. On a miss it walks backward, at most 20 blocks. It can only find entries that earlier requests wrote. It never finds stable content behind your breakpoint. That is why long agent runs need intermediate breakpoints, not one at the end.

Read the usage object back to the whole input

Anthropic's usage object splits the input three ways. The pieces sum to the total.

usage.input_tokens                        tokens after the last breakpoint
usage.cache_read_input_tokens             served from the entry, at the read rate
usage.cache_creation_input_tokens         written into the entry, at the write rate
usage.cache_creation.ephemeral_5m_input_tokens   the split, by TTL
usage.cache_creation.ephemeral_1h_input_tokens

total_input = cache_read + cache_creation + input

TTL is time to live, the lifetime of a cache entry. Check this identity on your first run. If the pieces do not sum, your adapter dropped a field.

Choose the TTL by the gap between calls

The 5-minute tier writes at 1.25x. The 1-hour tier writes at 2x. From the break-even formula you derived above, the 5-minute tier profits after one read. The 1-hour tier needs two reads before expiry.

So the 1-hour tier wins only when gaps between calls beat 5 minutes. Think of a human conversation with pauses, or a nightly batch. A fast tool loop never lets the 5-minute entry expire. There, paying 2x buys nothing.

Tool loop, 20-second gaps: 5-minute tier, 1.25x write. Entry refreshes every turn. Profits from read one.

Same loop, 1-hour tier: 2x write premium paid. The longer lifetime is never used. Pure waste.

The two-tier table is an Anthropic shape. Both providers now ship both caching modes. OpenAI GPT-5.6 and later supports explicit breakpoints and TTL options. Anthropic also offers automatic caching with one top-level cache_control field. The old table, OpenAI automatic versus Anthropic breakpoints, is stale.

The multipliers are dated, so your formula must not be

Three verified values carry their conditions. The 1.25x OpenAI write price applies to GPT-5.6 and later. Earlier models charge nothing extra for writes. The 1,024-token OpenAI minimum is also a current-model value, and it counts visible tokens only.

Anthropic reads are no longer a flat 0.1x. On Fable 5.1 and Mythos 5.1, reads are 0.025x base input. On Opus 5.5, they are 0.05x. A meter hardcoding 0.1x under-reports savings on those models. The break-even formula survives all of this. The constants do not.

Checkpoint

Five scenarios, no notes. Write your answer first, then open the sketch. The maths questions want the numbers, not the principle.

  1. Show the math. A model charges, per million tokens: input $2.00, cached input $0.20, cache writes $2.50, output $12.00. Your agent step sends 20,000 input tokens. 18,000 of them hit the cache. The step generates 400 output tokens. (a) Compute the true cost. (b) Compute what your Phase 1 two-price meter (input price, output price) reports. (c) How many times higher is the old number? (d) Finance prices customers from the old number. Name the business error.
    Answer sketch

    (a) Uncached input: 2,000 x $2.00 / 1e6 = $0.004. Cached input: 18,000 x $0.20 / 1e6 = $0.0036. Output: 400 x $12.00 / 1e6 = $0.0048. True total: $0.0124.

    (b) 20,000 x $2.00 / 1e6 + $0.0048 = $0.0448.

    (c) $0.0448 / $0.0124 is about 3.6x.

    (d) You price against a cost 3.6x above your real cost. You lose deals you could have won, and you cannot explain your margin when someone checks the invoice.

  2. Caching is on, the invoice did not move. A colleague concludes caching does not work for your workload. Give three separate causes. For each, name the one number you would check.
    Answer sketch
    • The prefix is below the model's minimum. Nothing caches, and no error is returned. The cached-token count is exactly 0 on every call.
    • Something volatile sits early in the prompt, so every request is cold. The cached count is also 0. Lengthen the test prefix above the minimum: if it still reads 0, the cause is volatility, not length.
    • The saving is real but your meter never reads the cached-token field. Check whether your code reads it at all. If not, your cost number can never move.

  3. Pick the tier. The provider charges 2x input for a 1-hour write, 1.25x for a 5-minute write, 0.1x for a read. (a) Derive the reads needed before the 1-hour tier profits. (b) Your agent calls every 12 minutes for an hour. Which tier? (c) Your agent calls every 20 seconds for two minutes, then stops. Which tier, and why is the answer different?
    Answer sketch

    (a) (2.00 - 1.00) / (1.00 - 0.10) = 1.11, so two reads.

    (b) At a 12-minute gap a 5-minute entry always expires before the next call: a write every time, zero reads. The 1-hour tier gives one write and four reads in the hour, and four reads clears the two-read break-even. Pick one hour.

    (c) Calls 20 seconds apart never let a 5-minute entry expire, so the cheaper 1.25x write is already reused. The extra 0.75x buys nothing. Pick five minutes.

  4. This is broken. Your dashboard reports $0.24 for an agent run. The provider billed $0.52. The dashboard shows 20 input tokens and 13,545 output tokens, on a many-turn run with a large system prompt. (a) Name the cause. (b) Why should 20 input tokens have looked wrong to any reader? (c) Name the two missing usage fields. (d) Why did this pass code review?
    Answer sketch

    (a) The instrumentation never forwarded cache-read and cache-write tokens, so the tool recomputed cost from partial counts.

    (b) On that provider, input_tokens counts only the tokens after the last cache breakpoint. A many-turn run with a large system prompt cannot have 20 real input tokens. The tool read the field as total input. It is not.

    (c) cache_read_input_tokens and cache_creation_input_tokens.

    (d) The wrong number looks plausible, comes through the same code path as correct numbers, and raises no error. Only a comparison with the provider's own bill catches it.

  5. Walk it through. Ten identical requests arrive at once, at cold start, each with the same 12,000-token system prompt. Writes cost 1.25x. (a) Trace what the cache does across the 10 requests. (b) Compare total input cost with caching off. (c) Name the one change that fixes it, and its latency cost.
    Answer sketch

    (a) An entry becomes usable only after the first response begins. All 10 requests start before any entry exists, so all 10 write and none read.

    (b) The burst costs 1.25x the no-cache run. At $2.00 per million input tokens, that is $0.300 against $0.240. Caching made this burst more expensive.

    (c) Send one warm-up call, wait until its response starts, then fire the other nine at the warm entry. The cost is one extra round trip at the start of the burst.

The break-even formula and the total-input identity answer all five questions; everything else is plugging in.
