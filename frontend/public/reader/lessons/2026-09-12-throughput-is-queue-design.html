Throughput is queue design

AI systems — serving. Also feeds the phase 3 replica build. Sources: vLLM's engine anatomy, and MySQL replication internals.

The one idea

A fast thing feeds a slow thing. That join is a seam.

In MySQL replication, the fast thing is the primary — thousands of row changes a second. The slow thing is the replica, which by default applies them one transaction at a time.

In vLLM, the fast thing is prefill: the GPU reads a whole prompt in one pass. The slow thing is decode: one token per step, and every step reads the model's entire weights from memory.

When work arrives faster than the slow side can take it, you have exactly two options:

  • Buffer it. Accept the work, park it somewhere, fall behind.
  • Refuse it. Don't accept it yet. Make the caller wait at the door.

That's the whole lesson. Everything else is detail on those two options — and on one question: who pays?

MySQL buffers

Two threads run on the replica. The I/O thread pulls events from the primary and writes them, unchanged, into a local file — the relay log. That file is the buffer. The applier thread reads that file and actually executes the changes.

When the primary runs hot, the I/O thread keeps up easily; it is only copying bytes. The applier falls behind. The unapplied part of the relay log grows. Nothing errors. Disk fills quietly.

About Seconds_Behind_Master. People read it as "how big the backlog is". It isn't. It compares the timestamp of the event the applier is working on right now against the replica's clock — so it measures applier delay only. If the network dies and the I/O thread stops pulling, the applier finishes what it has and this reports 0, while you are minutes behind. Zero means "healthy" or "receiving nothing", and you cannot tell which from that number alone. Always read Replica_IO_Running beside it.

vLLM refuses

vLLM keeps two queues: waiting and running.

To generate tokens, the GPU must hold that request's attention keys and values — the KV cache. vLLM allocates it in fixed chunks of 16 tokens, called blocks.

The rule: a request moves from waiting to running only if the cache manager can guarantee enough blocks for its next step. No blocks, no admission.

Notice what that protects. A request already generating never stalls halfway for want of memory. The cost lands on the new request's time to first token instead.

Refusing is cheap here because of the batch layout: all sequences are concatenated into one flat row of tokens with no padding, so a request can join or leave at any token boundary. That is what continuous batching means — the batch is re-formed every step, not held until its slowest member finishes.

Buffering hides the problem and costs freshness. Refusing shows it immediately and costs admission latency. A seam that appears to cost nothing is hiding the cost somewhere you are not measuring.

The third move: chop the big job

Once you have buffer and refuse, one more lever appears: make the big item smaller.

A 100,000-token prompt processed in one step holds the GPU for seconds, and every request already generating gets nothing. That is head-of-line blocking: one big job at the front stalls everyone behind it.

Chunked prefill caps how many prompt tokens are processed per step, spreading a long prompt over several steps, each one still carrying the ongoing decodes. The long request's first token arrives later; everyone else keeps a smooth stream. The knob is --max-num-batched-tokens: the per-step token budget shared between prefill chunks and decodes.

Two more vLLM moves, same reasoning:

  • Prefix caching. If two prompts share their first 16-token block, that block's KV is computed once and reused. The best way through a seam is not to send the work at all. Only complete blocks are cached, so a prompt ending mid-block recomputes its tail.
  • Speculative decoding. Decode is limited by memory bandwidth, not arithmetic — the math units idle while weights are read. So a small cheap model guesses several tokens ahead and the big model verifies them in one pass. A rejection sampler keeps the output distribution identical to the big model's own.

One knob that lies

Semi-synchronous replication makes the primary wait for at least one replica to confirm receipt before reporting commit. It sounds like durability. The default timeout is 10 seconds, and on timeout the primary silently falls back to plain asynchronous replication and carries on.

So the guarantee holds while the network is fast and disappears exactly when the network is slow — the only time you needed it. It does not warn you. If you need a real durability bound, that is consensus, not semi-sync.

Fifteen minutes today

Watch a buffer fill. Two containers, mysql:8.4.

# docker-compose.yml
services:
  primary:
    image: mysql:8.4
    command: --server-id=1 --log-bin=binlog --gtid-mode=ON
             --enforce-gtid-consistency=ON
    environment: { MYSQL_ROOT_PASSWORD: root }
    ports: ["3306:3306"]
  replica:
    image: mysql:8.4
    command: --server-id=2 --read-only=ON
    environment: { MYSQL_ROOT_PASSWORD: root }
    ports: ["3307:3306"]

Row-based binlog is already the default in 8.0+, so you do not need to set it.

-- primary
CREATE USER 'repl'@'%' IDENTIFIED BY 'repl';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';
CREATE DATABASE bench;
CREATE TABLE bench.t (id BIGINT PRIMARY KEY AUTO_INCREMENT, v INT);

-- replica
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='primary', SOURCE_PORT=3306,
  SOURCE_USER='repl', SOURCE_PASSWORD='repl',
  SOURCE_AUTO_POSITION=1;
START REPLICA;

Now freeze the slow side while the fast side keeps going:

-- replica: stop applying, keep receiving
STOP REPLICA SQL_THREAD;

-- primary: insert in a loop for a minute
-- replica: watch it climb
SHOW REPLICA STATUS\G

Read three fields together, never one:

  • Replica_IO_Running — still Yes? Then you are receiving.
  • Seconds_Behind_Master — climbing. That is applier delay.
  • Relay_Log_Space — growing. That is the buffer, in bytes.

Then START REPLICA; and time the drain. Run it again with SET GLOBAL replica_parallel_workers = 4; and compare. (In 8.4, transactions already carry WRITESET dependency information by default, so non-conflicting ones apply in parallel. On 8.0 you set binlog_transaction_dependency_tracking = WRITESET yourself; that variable is deprecated now.)

You have just built the observable half of your phase 3 replica build — a lag counter — before writing any Go. And the build itself? If the Bitcask-style store from phase 2 is not running yet, there is nothing for a replica to attach to. Reading has outrun building.

Where it breaks

  • Seconds_Behind_Master = 0 can mean "disconnected". Always check Replica_IO_Running too.
  • Statement-based replication diverges silently. SYSDATE(), UUID(), RAND(), LIMIT without ORDER BY, and user-defined functions give different answers on the replica. No error — wrong data, found weeks later. (NOW() is safe: the statement's timestamp is replicated with it. That is exactly why SYSDATE() is not — it reads the clock at execution.)
  • Row-based apply needs primary keys. The applier finds each row by primary key. Without one, every UPDATE and DELETE is a full table scan on the replica, one event at a time.
  • A weak replica cannot absorb, only fall behind. Less CPU or slower disk than the primary, and parallel workers will not save you: the drain rate sits structurally below the fill rate.
  • Chunked prefill is not free. The long request's first token gets slower and prefill runs slightly less efficiently. Right trade with many concurrent users, wrong one when a single request owns the machine.
  • Prefix caching only shares complete blocks. A prompt ending mid-block recomputes that tail every time.

Two posts you could write

  • "Seconds_Behind_Master lies to you twice." It measures applier delay, not backlog, and reads 0 when you are disconnected. Yours because you can demo both states with two containers.
  • "A vLLM scheduler and a MySQL replica solve the same problem." At every seam you buffer or refuse, then choose who pays. Yours because you can put KV-block admission beside the relay log with real flags and real status fields.
