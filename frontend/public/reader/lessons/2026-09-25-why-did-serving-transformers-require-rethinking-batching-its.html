Why did serving Transformers require rethinking batching itself?

What in a Transformer actually breaks when requests leave and join a batch mid-generation, and why the fix costs almost nothing

Continuous batching reads as obvious in retrospect: when a request finishes, evict it; when capacity frees, admit a new one; repeat every decoding step. If you built a scheduler this year, that is the baseline you would start from. But in 2022 the standard engines, NVIDIA's FasterTransformer and Triton Inference Server, ran each batch as a unit from prefilled prompt to the last generated token, and capable teams shipped that on purpose.

If the fix was so obvious, those teams would have shipped it. They did not, and the reason is not that eviction is hard to implement. It is that iteration-level scheduling makes the batch irregular: at any step, the requests you must run forward have processed different numbers of tokens. That looks like it breaks the one thing batching exists for, the ability to run many requests through the model in one set of GPU operations. The question this lesson answers is which part of the Transformer block actually breaks, because knowing that is what lets you read a claim like "36.9x higher throughput" and say where the gain lives before you believe it.

What did request-level scheduling waste, in a trace you can picture?

Request-level scheduling wastes compute and delays clients, and you can see both in four iterations.

Predict: a batch of two requests, one finishes at iteration 2, one at iteration 4. When can the first client's answer leave the server?

At iteration 4. Under request-level scheduling the batch is a unit: the engine runs it until every request finishes. The finished request's slot keeps computing for two more iterations, and its client waits. This is the wrong the scheduler loop in your phase fixes.

Put yourself behind a serving cluster in 2022. A client sends a prompt that needs two tokens of answer. Another sends one that needs four. Your engine batches them together, because batching is how you keep the GPU fed. Here is what the trace looks like.

Two distinct wastes hide in this picture, and they have different victims. First, the finished request cannot return. Request A produced its last token at iteration 2, but the client waits two more iterations, and the GPU spends those iterations computing a slot that produces nothing.

Second, late joiners queue behind someone else's output length. A request arriving at iteration 2 waits until iteration 4, because the current batch runs to completion as a unit. Queueing delay now scales with the longest generation in flight, a number the new request has nothing to do with.

Both wastes come from one design choice: the batch boundary is the request, not the iteration. For ResNet or BERT this cost nothing, because every request needs exactly one forward pass and the whole batch finishes together. Autoregressive generation breaks the assumption. Each request needs an unknown number of iterations, so a fixed batch guarantees that some slots outlive their requests and some arrivals outwait them.

Why did running one iteration at a time look impossible?

The irregular batch has exactly one blocker, and it is not a weight layer.

Scheduling one iteration at a time frees the scheduler, but it breaks the tensor. Every request now sits at a different token position within the same iteration. A GPU kernel expects one rectangular tensor, and this batch is not rectangular.

Predict: request A is 12 tokens in, B is at token 3, C just arrived. Which operation in the block stops you from running all three as one flat tensor?

The natural guess is a weight-bearing layer, since weights dominate the model. In fact every weighted op flattens without complaint. The blocker is attention: the one operation with no weights of its own. A Linear maps each token's vector independently, so rows from different requests never meet. But A's twelfth token must attend to A's past tokens, and only A's. The request boundary lives in exactly one place.

Start from why batching pays at all. Weights live in GPU memory, and reading them costs time. A batch reads the weight matrix once and spends that read across every token. Amortizing weight reads is the whole benefit.

Linear, LayerNorm, Add and GeLU are position-wise: each output row comes from one input row. No row cares which request produced it. So flatten the batch into one token-wise tensor of shape [ΣL, H], where ΣL counts all tokens in the iteration. Four requests holding seven tokens become a single [7, H] tensor.

The Q, K and V projections are Linear layers, so they flatten with the rest. The remaining score computation has no parameters, and the paper says so in one sentence. "Since the Attention operation is not associated with any model parameters, applying batching to Attention has no benefit of reducing the amount of GPU memory reads by reusing the loaded parameters across multiple requests." Per-request attention gives up no amortization, because there are no weights to amortize. One rule remains: a token never scores against another request's keys.

That leaves the execution shape: Split the flat tensor per request, attend each against its own stored keys and values, then Merge back into [7, H]. Orca calls this selective batching.

What does the 36.9x number actually claim, and what did the paper leave open?

The 36.9x is a scheduling-efficiency claim with a baseline attached, not a general speedup.

You have Orca's two ideas now: iteration-level scheduling and selective batching. The paper's abstract reports what they bought together: 36.9x throughput over NVIDIA FasterTransformer at the same level of latency, on a GPT-3 175B model. The baseline is the era's request-granularity scheduler, and latency is held fixed.

Two further conditions come from reading notes, not the paper text (unconfirmed). Runs used synthesized client request traces and models matching the GPT-3 architecture at 13B, 101B, 175B and 341B, because real GPT-3 checkpoints were not public. Read 36.9x as a scheduling-efficiency result at one architecture, not a measurement of a production GPT-3.

The paper leaves one hole unmeasured. Nothing in the design manages where K/V states sit. Reading notes say they are pre-reserved per request (secondary). vLLM's verified text confirms earlier systems reserve a chunk for the maximum sequence length.

Predict: an Orca-style server pre-reserves each request's full K/V in GPU memory. What fraction of it held real tokens? Guess a percentage.

Well over half is the reasonable guess. The measured answer: only 20.4 to 38.2 percent of the K/V cache memory held actual token states. The rest was reserved for tokens never emitted, or lost to fragmentation between fixed chunks.

What this changes in the course

Your phase teaches continuous batching as a scheduler feature: swap requests in and out between decode steps. The paper shows that is only half of it. The deeper move is a tensor-layout argument. Requests of different lengths cannot share one tensor. So you flatten every operation except attention into one [ΣL, H] tensor and split only where attention needs request boundaries. The scheduler decides who runs. The layout decides that an irregular batch is runnable at all.

That reframing explains why Phase 2A has a memory half. Once lengths vary freely, each request still holds state across iterations: its growing K/V. Orca left that state pre-reserved and unmanaged. vLLM later measured only 20.4 to 38.2 percent of it holding real tokens. Scheduling fixed when requests move. Memory layout fixed how much room they have to exist.

Keep both layers in mind going forward. When you read any serving engine, ask two questions. First: what is the scheduling granularity? Second: how is per-request state stored across iterations? Orca answered the first and ignored the second. The next section is the answer to the second, and it borrows its idea from operating systems: pages.

Checkpoint

Two questions. Use the mechanism, then open the answer.

Q1. Your teammate profiles decode and sees the attention kernel at low utilization. He proposes a custom kernel that batches attention across requests, so all queries in the iteration run in one call. Can this give the gain he expects, and what would you measure first?

Answer sketch

Batching attention does not amortize weight reads, because attention has no weights. The redundant work batching removes is reading model parameters once per request, and attention loads only the per-request K/V, which is already different per request. Merging requests into one kernel call cannot remove those reads. So the expected gain is small: at best, fewer kernel launches and better scheduling inside the launch.

Measure first whether attention is slow because it is memory-bound on K/V reads or because of launch overhead. On decode, each request's query is one token, so the kernel reads megabytes of K/V to multiply against a vector of length one. It is memory-bound, and utilization of compute units being low is the expected state, not a fixable defect. If launch overhead were the cause, you would see idle gaps between kernels, not a slow kernel.

Q2. A colleague reads the Orca result and concludes the 36.9x came from splitting and merging tensors around attention. What is his mistake?

Answer sketch

Selective batching is what made iteration-level scheduling possible; it is not what bought the throughput. The 36.9x against FasterTransformer on GPT-3 175B at similar latency comes from scheduling: finished requests leave immediately and new requests join at the next iteration, so the GPU stops computing dead slots. The Split and Merge changed no math and saved no work by itself. It removed the excuse for keeping batches fixed. Also note the conditions on the number itself: synthesized request traces, and models matching the GPT-3 architecture rather than real GPT-3 weights (secondary, from reading notes). Treat 36.9x as a scheduling-efficiency number against a 2022 baseline, not a universal gain.

Post

Post 1. Serving Transformers needed new batching for one reason. Batching exists to amortize weight reads, and attention has no weights. Orca flattens every request's tokens into one [ΣL, H] tensor, runs Linear and LayerNorm on all of it, Splits for per-request attention, Merges back. The irregular batch stops being a problem. Yours because you can draw the Split/Merge shape and point at it in vLLM's source.

Post 2. "36.9x faster" is a headline with a baseline attached. Orca beats FasterTransformer 36.9x in throughput at similar latency, on GPT-3 175B, with synthesized traces. The number measures scheduling waste in the 2022 baseline, not a production speedup. Read every systems paper this way: the multiplier only means what its baseline wastes. Yours because you read the primary source and kept its conditions.
