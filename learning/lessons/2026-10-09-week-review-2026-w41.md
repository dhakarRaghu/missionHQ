### The freeze

Prefill and decode share one forward pass through the model. One long prompt therefore either waits behind a token budget or runs in one pass. It then stops every decoding stream while it runs. The budget is the dial between those two choices, so it is a product decision, not a tuning detail.

You read such a pause in the maximum inter-token gap, the longest time between two tokens of one response. Your time-to-first-token and total-time medians cannot show it. The pause sits in the middle of a stream that already started. This idea came in \"The five things worth keeping\" below. The queue lesson of 2026-09-12 gave it its base. Throughput is queue design, so a pause is a scheduling choice. The question from the 2026-09-25 paper session is whether continuous batching removes the freeze or only moves it. It is the same idea one level down.

### The window and the schema

A bigger context window does not remove the budget problem, it only postpones it. Accuracy falls with input length and with where in the prompt a fact sits, well before the token limit. You therefore treat the window as a budget split into zones. Room is kept for the reply and for the summarising call.

## Three questions from older material

Q1: the freeze, in numbers

A server uses the cost model from batching_sim.py: prefill costs 0.03ms per token, each decode step costs 18ms plus 0.12ms per decoding request. Three requests are decoding. A 24,000-token prompt arrives, and the token budget, the maximum tokens processed in one iteration, is 2,048.

- How long do the three streams freeze if the prompt runs in one pass, without chunking?

- With chunked prefill, how many prompt tokens fit in each iteration, and how many iterations does the prompt need?

- How long is each chunked iteration, and what do the streams feel now?

Answer sketch

- 24,000 × 0.03 = 720ms. The three streams get no token during that pass. In the default measured run the worst gap is 764ms, because the decode passes sit on each side of it.

- The budget reserves 3 tokens for the decodes, so 2,048 − 3 = 2,045 prompt tokens fit per iteration. 24,000 / 2,045 = 11.7, so the prompt needs 12 iterations.

- 2,045 × 0.03 + 18 + 0.12 × 3 = 61.35 + 18.36 = 79.7ms per iteration. The streams now pause about 80ms per token instead of 720ms once. The measured worst gap is 81ms, because the real batch holds more decodes than three.

Q2: the schema that cost 9 points

Your classification service returns valid JSON that matches the schema on every call, and finish_reason is stop. Accuracy still dropped 9 points after you enabled strict mode last week. Your labeled set has 12 items.

- Give the most likely cause.

- Describe the exact schema change you would test, including its place in the property order.

- Name the measurement that would settle it, and say why one run is not enough.

Answer sketch

- The schema forces the model to commit to the label field early, with no room to reason in text first. The tax comes from asking for the format, not from the decoder enforcing it.

- Add a reasoning string field as the first property, before the constrained fields, and add it to required with additionalProperties: false. A reasoning field placed last changes nothing, because decoding runs left to right.

- Run the same labeled set through both schemas with structured_lab.py and use --repeat. Sampling varies between runs, so on 12 items a 9-point gap can appear by chance.

Q3: the rule that must cross the boundary

Your agent runs 200 tool-calling steps over several hours. A policy rule says it must never issue a refund above 200 EUR. The context will be compacted several times in that span. Design the context strategy: the trigger, what you copy, what you summarise, and what you drop.

Answer sketch

- Trigger at a fixed token threshold well below the window, for example 50% to 60% of it, checked before every call.

- Copy word for word: the refund limit rule, every other policy constraint, and the last few turns.

- Summarise the earlier conversation into decisions, constraints, and open items.

- Drop full tool results and replace them with pointers you can fetch again, such as an order id.

The justification is the ConstraintRot measurement: 0% violations when the constraint survived compaction as literal text, 38% when it was dropped. So the refund rule must never depend on what the summariser found interesting. And the summarising call is a second billed call, so add its cost to the same run record.
