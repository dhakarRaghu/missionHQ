## What you read this week

One long prompt freezes every stream

Prefill and decode share one forward pass and one token budget. So a long prompt either waits or pauses every stream sharing its pass. Chunked prefill converts that pause into a small rise in time to first token. In Phase 2B you watched mean TTFT stay green while one stream paused for 720 ms.

A cache hit is two promises

A hit proves the key matched; it says nothing about the stored state behind it. The insert path stamped a short key on a newer state. Every later hit resumed from 192 tokens in the future, and every metric read success. Only cold-warm output equality at temperature 0 proves the value is right.

The same field name, two meanings

OpenAI counts cached tokens inside usage.input_tokens and Anthropic counts them outside it. One shared summation is wrong by the size of your cached prefix. A cache that breaks returns 200 either way. The cached-token count in the usage object is the only proof caching happened.

A 200 never proves enforcement

An OpenAI-compatible server can accept a constraint parameter, parse it, and never enforce it, and it answers 200 throughout. The lesson from the ignored parallel_tool_calls=false flag: treat engine flags as hints. Enforce the invariant in your own layer, the one that executes the tool calls.

A cascade pays for some queries twice

An escalated query costs the cheap answer and the deep answer. So a cascade saves money only while the escalation rate stays under 1 minus the price ratio. Accuracy and cost alone cannot prove the signal works. A coin-flip cascade can show the same numbers. Only a random control that escalates the same count separates signal from noise.

Three rules broke a four-month incident into ten requests

A broken cache moves money between billing classes while the token count stays flat, so a token chart sees nothing. The floor is set just below the measured normal. Per-request cost plus per-request cache hit rate detects in under ten requests what a 50% floor only caught after 59. And only a pre-call reservation priced at the max_tokens worst case stops spend before it happens. Every post-hoc control enforces against stale spend.

A 408 is usually not the engine

A non-streaming long request holds one silent connection. The shortest idle timeout in the chain kills it however healthy the engine is. Scaling the engine was the tempting first move and the wrong one. The fix is streaming or a keepalive on the path that actually timed out.

A borrowed benchmark cannot gate your quantization

A benchmark measures only the tasks it samples. Quantization damage lives mostly outside that sample: human raters measured 16.0% worse where the automatic suite measured 1.7%. Any gate you ship behind must be built from your own tasks, your own languages and your real context length.

You rent a clock, not a GPU

A rented GPU bills from container start. The weight download is billed at GPU rates, and one slow link can pass the whole hour. Price the session before t=0:00, and pick the machine by its measured downlink. Have every command written down before you rent anything.

## The five things worth keeping

Nine lessons passed this week, but only five mechanisms are worth keeping after the examples are forgotten. Each one below is a claim you can now test. It outlives the lesson that taught it because it is physics, not a bug report.

Prefill is parallel, decode is serial, and both share one token budget

A long prompt is processed in one parallel pass, so it is cheap per token. But that pass runs inside the same batch as every decode. One big prompt then freezes every stream that shares its forward pass. This outlives the example because it is the physics of the hardware. It explains why long prompts and long answers feel different. It explains why your mean TTFT can stay green through a 720ms pause. And it explains why every server you will ever run needs a token budget that reserves decodes first. From "Why does one long prompt freeze every stream?"

Strict mode guarantees legal tokens, finish_reason guarantees the end

A grammar mask removes illegal tokens at every step. So the shape of the output is guaranteed and nothing else is. Truncation follows the schema perfectly and still cannot be parsed. That is why the finish_reason check must stay exactly when teams want to delete it. And the accuracy tax is mostly paid at the prompt, 3.9 of 5.5 points, before any mask runs. This outlives the example because any constraint system you adopt will have the same split. It is what it enforces per step, and what it never enforces about the whole. From "Strict mode says the tokens are legal. Who says the answer is complete?"

A hit rate counts keys, so only output equality proves the value

A cache hit is two promises: the key matched, and the stored state is the right state. Your dashboard checks the first promise only. So a clamped snapshot can serve a state from the future while every metric reads green. The regression check is one job. Run the same prompt cold and warm at temperature 0 and diff the token IDs. That is because a correct cache changes cost but never content. This outlives the example: every cache you will build has the same two promises and the same blind spot. Prefix cache, snapshot cache, memoised tool result are examples. From "What catches a value lie before your users do?"

Detect billing regressions on per-request cost and per-request hit rate

A broken cache moves tokens between billing classes. So the token count never moves and no token chart can see it. What moves is per-request cost and per-request cache hit rate. The floor must sit just below the measured normal. A tidy 50 percent floor on a 98 percent workload fires nine requests late. This is what turned a four-month incident into a ten-request incident. It outlives the example because "alert on the rate, not the volume" is the right shape for any shared-resource regression. From "Which three rules catch what the token chart cannot?"

You rent a clock, not a GPU

A rented GPU bills from container start. So the weight download, the image pull and your typing are all billed at GPU rates. The fix is to price the session before t=0:00. Pick the machine by its measured downlink, and write every command into a text file while it costs nothing. This outlives the example because it is the rule for any resource billed per second. Preparation happens on the free clock, execution on the expensive one. From "Why is typing the launch command the last thing you do?"

## Three questions from older material

These three questions are old material answered cold. The numbers sit inside each question. Each answer sketch shows the arithmetic, so cover the sketch and work it before you open it.

### Question 1: the creeping TTFT (Phase 1)

Your support agent's TTFT crept from 400 ms to 1,200 ms over two weeks of sessions. Someone says the provider's GPU got slower. Usually the real change is your own context growing, because agent frameworks append history silently. Your prices are $2.00 per million input tokens and $12.00 per million output tokens.

(a) Decompose TTFT into queue and prefill. (b) Decompose the cost. (c) Say why total latency is the wrong number to diagnose this with.

Answer sketch
(a) Prefill is the parallel read of the whole prompt. So 6,000 tokens at 15,000 tokens per second is 400 ms. TTFT = queue + prefill, so the queue is 1,200 − 400 = 800 ms.

(b) Input: 6,000 × $2.00 / 1e6 = $0.012. Output: 250 × $12.00 / 1e6 = $0.003. Total $0.015, and 80 percent of it is the prompt.

(c) Total latency fuses the one number you control, prompt size. It fuses this with the two you do not, queue and per-token decode speed. Here the 13.7 s mixes 800 ms of queue, 400 ms of prefill and 12.5 s of decode. TTFT creeping while sessions age is usually your own context growing. The framework appends history silently, so the prompt and its prefill bill grow every turn. Read TTFT and the input-token count per call, and the cause shows.

### Question 2: the timestamp again, priced properly (Phase 0, with Phase 3A arithmetic)

Back in Phase 0 the one-second timestamp in the system prompt broke an 18,000-token cached prefix and multiplied the bill. Now you can price it exactly. Prices per million tokens: input $2.00, cached input at a 90 percent discount ($0.20), cache writes $2.50. The timestamp changes the prefix every second, so every request writes a new entry that expires unread.

(a) Express write and read as fractions of input price. (b) Compute the break-even read count from (write − 1) / (1 − read). (c) Compute the multiplier on the 18,000-token prefix, before and after the timestamp line.

Answer sketch
(a) Write = 2.50 / 2.00 = 1.25. Read = 0.20 / 2.00 = 0.10.

break-even reads = (1.25 − 1) / (1 − 0.10)
                 = 0.25 / 0.90
                 ≈ 0.28 reads

So one read of an entry already puts it in profit. Caching is cheap, when the prefix holds still.

(c) With a stable prefix, 18,000 tokens cost 18,000 × $0.20 / 1e6 = $0.0036 per request. With the timestamp, those tokens are a fresh write at $2.50: 18,000 × $2.50 / 1e6 = $0.045. The multiplier is 0.045 / 0.0036 = 12.5x on the cached part of every request. One line of prompt, priced exactly: the discount was 10x, and the write surcharge added 1.25 on top.

### Question 3: measure before you buy (the RAG recall lesson)

Phase 3A's rule was that a cache hit is only free when the stored value's geometry matches the key. The test that proves it is the warm-cold equality check. Run one prompt cold, then warm at temperature 0, and diff the output token IDs. Your teammate now proposes buying a second cache tier, the summary snapshots that caused the geometry bug. In the spirit of "measure recall before you buy infrastructure", there is a question. Can the equality test run before the second tier exists, or does it need the new hardware first?

Answer sketch
It runs today, on the cache you already own. The test needs only a cache that can be warm. It needs any cache you own, two runs of the same prompt at temperature 0. It also needs a diff of the token IDs. The single-tier prefix cache is enough. A correct cache changes only cost, never content. So any drift between the cold and warm runs convicts the stored value on the current infrastructure. This happens before a dollar moves.

This is the same shape as measuring recall against a golden set before buying a vector store. The measurement is a query and a comparison, both free. The purchase is the thing it gates. The CI version is one job. Run the shared harness prompt cold and warm, assert equality, fail the build on drift. When the second tier arrives, the same job becomes its acceptance test. The clamp bug would have failed the build on day one instead of running for months.
